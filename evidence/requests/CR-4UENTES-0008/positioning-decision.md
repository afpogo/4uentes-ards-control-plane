# Decision De Posicionamiento Del Portfolio - CR-4UENTES-0008

## Decision

Usar un posicionamiento publico `employment-first` para `4uentes-portfolio`.

El portfolio debe presentar a Andres Pogo Fuentes principalmente ante
recruiters tecnicos, hiring managers y lideres tecnicos que evaluan roles de
software engineering.

El posicionamiento orientado a clientes o consultoria puede quedar como
secundario y exploratorio hasta que exista una taxonomia de servicios aprobada
por el owner y reflejada en contenido visible del portfolio.

## Baseline De Posicionamiento Publico

Narrativa principal:

- base de integracion enterprise y backend;
- experiencia de delivery fullstack;
- delivery frontend con React y TypeScript;
- background Java/Spring y sistemas de integracion;
- exposicion a CI/CD, Docker, AWS y colaboracion de producto;
- transicion desde sistemas enterprise hacia web/product engineering moderno.

La evidencia mas fuerte es el historial profesional y las descripciones de
experiencia aprobadas por el owner. Los proyectos publicos y certificados son
evidencia de soporte.

## Taxonomia De Evidencia

Usar estas etiquetas para futuros cambios de UI/contenido:

- `professional_experience`: historial laboral, rol, contexto,
  responsabilidad, stack, impacto y evidencia high-level de delivery
  enterprise.
- `public_project_evidence`: repositorios publicos inspeccionables, demos,
  paginas de proyecto o screenshots.
- `demo_or_learning`: practica, curso, prototipo o repositorios
  experimentales.
- `certification_support`: certificados y assets de conocimiento que soportan
  claims de skills.
- `private_enterprise_evidence`: trabajo enterprise descrito sin exponer
  detalle confidencial de implementacion.
- `contact_asset`: GitHub, LinkedIn, CV, email y otros caminos de contacto
  aprobados por el owner.

## Reglas De Cuidado

- No presentar la relacion 4uentes/SST como ownership publico de producto hasta
  que el owner apruebe wording exacto.
- No afirmar impacto productivo, resultados de cliente o seniority solo por la
  existencia de repositorios GitHub.
- No exponer datos de repos privados, organizaciones privadas, clientes,
  emails extraidos de commits, patrones de actividad, zona horaria ni horarios
  de trabajo.
- No autopublicar copy generado por IA o derivado de GitHub.
- Mantener GitHub enrichment como flujo editorial o build-time salvo que un
  request futuro apruebe comportamiento runtime.

## Siguiente CR Recomendado

Abrir un CR con mutacion de repo hijo para aplicar esta taxonomia primero a
owner docs y despues a contenido visible en cortes pequenos:

1. adopcion de taxonomia en owner docs;
2. etiquetas de evidencia para proyectos;
3. pasada de copy sobre experiencia;
4. politica de exposicion de contacto;
5. revision opcional de evidencia GitHub con repo allowlist explicita.
